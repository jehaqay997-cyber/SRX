# SRX Backend — Development 0.25.3

## الهدف من هذه النسخة
هذه نسخة تطويرية مشتقة من الحزمة المستعادة 0.23.0، وليست استعادة كاملة لآخر Backend الموصوف في سجل Replit. يركز هذا التحديث على مصادقة OIDC ذات توقيع موثّق، وفصل صلاحيات القراءة والكتابة، وسجل تدقيق يلتقط هوية المستخدم من الرمز الموثّق بدل حقول يرسلها العميل.

## المتطلبات والتشغيل المحلي
يتطلب Python 3.10+ ومزود هوية متوافقًا مع OIDC يصدر access tokens موقعة بـ RS256 ويكشف JWKS.

```bash
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows: .venv\Scripts\activate
pip install -e '.[test]'
cp .env.example .env  # ثم اضبط القيم في بيئة التشغيل؛ التطبيق لا يحمّل ملف .env تلقائيًا
export SRX_ENV=development
export SRX_OIDC_ISSUER='https://identity.example.org/'
export SRX_OIDC_AUDIENCE='srx-api'
export SRX_OIDC_JWKS_URL='https://identity.example.org/.well-known/jwks.json'
export SRX_DATABASE_PATH='./data/srx.sqlite3'
uvicorn srx_api.main:app --host 127.0.0.1 --port 8000
```

استبدل عناوين المثال بقيم مزود الهوية الفعلي. إذا لم تُضبط جهة الإصدار والجمهور وعنوان JWKS، تفشل الواجهات المحمية مغلقة وتعيد `503 AUTH_NOT_CONFIGURED`. لا تستخدم مفاتيح أو رموز اختبار في الإنتاج.

## المصادقة والتفويض
- جميع واجهات البيانات المحمية تتطلب Bearer access token صالحًا؛ يجري التحقق من التوقيع عبر JWKS، والجهة `iss`، والجمهور `aud`، و`exp` و`iat` و`sub`. خوارزمية التحقق مقيدة بـ RS256 في هذه النسخة.
- واجهات القراءة تتطلب النطاق `srx:read`.
- عمليات الإنشاء والتحقق من الحزمة تتطلب النطاق `srx:write`.
- الهوية المسجلة في `audit_events` تؤخذ من `sub` و`iss` بعد التحقق، ولا تُقبل من جسم الطلب. يسجّل حدث التدقيق ضمن معاملة التغيير نفسها، لذلك لا يُحفظ إذا فشلت المعاملة.
- في `SRX_ENV=production` تُعطّل واجهات Swagger وReDoc وOpenAPI تلقائيًا. تبقى `/v1/health` و`/v1/ready` عامتين في هذه النسخة.

## الاختبارات
```bash
pytest -q
```

تستخدم اختبارات المصادقة مفتاح RSA محليًا ومزود JWKS وهميًا؛ وهي تختبر منطق التحقق والصلاحيات وسجل التدقيق، ولا تثبت تكاملًا فعليًا مع مزود هوية خارجي أو نشرًا إنتاجيًا.

## حدود معروفة قبل النشر
- لا تزال إدارة قاعدة البيانات تعتمد على `CREATE TABLE IF NOT EXISTS` عند التهيئة؛ لا توجد ترحيلات Alembic موحّدة في هذه النسخة. لا تعتمد هذا المسار لتحديث قاعدة إنتاجية قبل بناء واختبار خطة ترحيل متوافقة مع المخطط الموجود.
- لم يُستعد بعد من المصدر الأصلي: وحدات Investigation، وPATCH السيناريوهات، وروابط support/challenge المنفصلة، وترحيلات Alembic المذكورة في سجل Replit. لم نُنشئ تاريخ ترحيل مزيفًا.
- أضيف حد لحجم جسم الطلب يفحص Content-Length مبكرًا ويقرأ التدفق على دفعات ويتوقف عند تجاوز الحد. ما زالت هناك حاجة إلى حدود معدل على مستوى التطبيق/الوكيل، وسجلات أمن مركزية، وإدارة أسرار الإنتاج، وترحيلات واختبارات استرجاع، والتكامل الفعلي مع مزود OIDC، وPostgreSQL، وفحص الاعتماديات.
- لا توجد في هذه النسخة خوارزمية توليد تنبؤات؛ درجات الترتيب ليست احتمالات، والاحتمال لا يُقبل إلا مع بيانات معايرة مصرح بها، ولا تُثبت صحة المعايرة بمجرد إرسال حقولها.
- لم يتم بناء أو تشغيل تطبيق Flutter.

## سجل الإصدار 0.24.3 — سجل المفاهيم والعلاقات
- إضافة `concepts` لتسجيل المفاهيم مع `system_id` ونوع المفهوم وحالته المعرفية: موثّق، متنازع عليه، مستنتج، أو اصطناعي.
- إضافة `concept_relations` مع مراجع مفاهيم منضبطة بمفاتيح أجنبية، وحدود `system_id`، وتصنيف لحالة الدليل، ومسوّغ نصي.
- العلاقة غير الاصطناعية تتطلب `source_id` موجودًا؛ هذا يثبت وجود مصدر مسجّل فقط، ولا يعني أن المصدر يثبت صحة الادعاء أو السببية.
- تسجيل عمليات الإنشاء في سجل التدقيق بهوية مأخوذة من رمز OIDC الذي تحقّق منه الخادم.
- واجهات جديدة: `GET/POST /v1/concepts` و`GET/POST /v1/concept-relations`؛ كلّها محمية بنطاق القراءة أو الكتابة المعتاد.
- فحوص جديدة تمنع المراجع المفقودة، وخلط `system_id`، والعلاقات الذاتية، وتسجيل علاقة غير اصطناعية بلا مصدر.

**التحقق المحلي:** اجتازت النسخة 43 اختبارًا (`pytest -q`). هذه نتيجة اختبارات محلية فقط، وليست تدقيقًا أمنيًا مستقلًا أو إثباتًا لسلامة النشر الإنتاجي.

**حدود باقية:** التهيئة لا تزال تعتمد `CREATE TABLE IF NOT EXISTS` ولا توجد ترحيلات Alembic موحّدة؛ لذلك لا تطبق هذه النسخة مباشرة على قاعدة إنتاجية قائمة قبل إعداد ترحيل مخطط واختباره على نسخة احتياطية. تم في 0.24.4 دمج توليد مسارات العلاقات المرشحة داخل API مع حدود حجم وعمق وعدد نتائج. تبقى المسارات فرضيات غير متحققة، ولا تستنتج الواجهة السببية ولا تولّد تنبؤات.

## فحص سلامة ترابط المصادر — 0.24.8

أضيف المسار المحمي `GET /v1/integrity/report` لإصدار تقرير قراءة فقط عن بصمات المصادر المكررة، والمصادر غير النشطة التي ما زالت مستخدمة في الملاحظات أو علاقات المفاهيم، وعلاقات المفاهيم المكررة. النتائج إشارات للمراجعة وليست أحكامًا بأن الادعاء كاذب أو أن المصدر غير أصيل. يتطلب المسار صلاحية `srx:read`.

### النسخ الاحتياطي المتحقق منه (SQLite)

يمكن إنشاء نسخة احتياطية وفحص سلامتها قبل اعتمادها:

```bash
python scripts/backup_sqlite.py ./data/srx.sqlite3 ./backups/srx-verified.sqlite3
```

لن تستبدل الأداة ملفًا موجودًا إلا باستخدام `--overwrite`. راجع `docs/MODERNIZATION_ROADMAP_AR.md` للقيود التشغيلية وخطة PostgreSQL/Alembic.


## تمرين الاستعادة المتحقق منها — 0.24.9

أضيف `scripts/restore_sqlite.py` لاستعادة نسخة SQLite متحقَّق منها إلى مسار مستقل. تتحقق الأداة من سلامة ملف النسخة قبل الاستعادة وبعدها، وتجهز الملف المؤقت في مجلد الوجهة ثم تنشره ذريًا. لا تستبدل وجهة موجودة افتراضيًا.

```bash
python scripts/restore_sqlite.py ./backups/srx-verified.sqlite3 ./restore-drill/srx-restored.sqlite3
```

هذا اختبار استعادة محلي لملفات SQLite فقط؛ لا ينشئ نسخًا خارج الموقع، ولا يثبت صلاحية خطة التعافي من الكوارث، ولا يدعم PostgreSQL بعد.


## تقرير جودة التنبؤ — 0.25.0

يوفر `GET /v1/forecast-quality` ملخصًا وصفيًا لدرجة Brier للتنبؤات التي سُجلت صراحةً كاحتمالات ولها نتائج مرصودة. تُستبعد درجات الترتيب والتنبؤات غير المقيمة. الدرجة الأقل أفضل داخل العينة المسجلة، لكنها لا تثبت المعايرة أو المهارة التنبؤية من دون خط أساس مناسب وفحص تحيز الاختيار واعتماد النتائج. يتطلب المسار صلاحية `srx:read`.


## أساسيات مفاتيح API — 0.25.1

أضيفت دوال مستقلة لتوليد مفتاح `ak_v1_` عشوائي بطول 256 بت وحساب بصمة HMAC-SHA-256 والتحقق منها بمقارنة ثابتة الزمن. يجب أن يأتي `pepper` من مدير أسرار أو متغير بيئة محمي، وألا يُخزّن في قاعدة البيانات أو المستودع. السلسلة السداسية القديمة لا تُقبل كتوكن بهذا التنسيق.

**حدود التنفيذ:** هذه primitives فقط؛ لم تتم إضافة مصادقة API-key إلى المسارات، ولا جدول مفاتيح أو واجهة إصدار/إلغاء أو تدوير. المصادقة الحالية عبر OIDC/JWT باقية كما هي. لا تستخدم المفتاح قبل بناء دورة حياة كاملة تشمل المالك والصلاحيات والانتهاء والإلغاء والتدقيق وعدم تسجيل القيمة الخام.


## دورة حياة مفاتيح API — 0.25.2

أضيفت مسارات إدارة مفاتيح API تحت مصادقة OIDC/JWT الحالية: `POST /v1/api-tokens` للإصدار، و`GET /v1/api-tokens` لعرض مفاتيح المالك المصادق فقط، و`POST /v1/api-tokens/{id}/revoke` للإلغاء. يُعرض السر الخام مرة واحدة فقط؛ قاعدة البيانات تحتفظ ببصمة HMAC، وبادئة قصيرة، والمالك، وتاريخ الإنشاء والانتهاء والإلغاء. كل إصدار وإلغاء فعلي يُسجّل في سجل التدقيق بهوية OIDC الموثقة.

قبل تمكين الإصدار، اضبط `SRX_API_TOKEN_PEPPER` على سر عشوائي قوي لا يقل عن 32 بايت، محفوظ خارج المستودع وقاعدة البيانات. إذا لم يكن مضبوطًا، تفشل عملية الإصدار مغلقة بـ503. مدة الصلاحية الافتراضية 90 يومًا والحد الأعلى 365 يومًا. **تنبيه:** هذه النسخة لا تقبل مفاتيح API بعدُ للمصادقة على بقية المسارات؛ مسارات إدارة المفاتيح لا تزال محمية بـOIDC/JWT. لا تضع المفتاح الخام في السجلات أو التذاكر أو المستودع.


## 0.25.3 — أساسيات رؤوس الأمان

- إضافة `X-Content-Type-Options` و`X-Frame-Options` و`Referrer-Policy` و`Permissions-Policy`.
- فرض `Cache-Control: no-store` و`Pragma: no-cache` على مسارات إدارة مفاتيح API لمنع تخزين الاستجابات التي قد تحتوي على السر المعروض مرة واحدة.
- إضافة HSTS عند `SRX_ENV=production`. يجب إنهاء TLS على التطبيق أو وكيل عكسي موثوق ومهيأ بصورة صحيحة؛ إضافة الترويسة وحدها لا تنشئ HTTPS.
- `.env` مستثنى من Git عبر `.gitignore`؛ استخدم `.env.example` للقيم النموذجية فقط، ولا تضع أسرارًا حقيقية فيه.
- لم تتم إضافة كلمات مرور محلية؛ مصادقة المستخدمين الحالية تبقى OIDC/JWT.
